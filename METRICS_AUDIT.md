## 3. Why these are the right first batch

**P0 selected: M1 (distributed lock concurrency), M2 (lock fail-closed), M3 (AI error classification correctness), M7 (atomic counter vs. naive read-modify-write).**

These four share a property the rest of the inventory doesn't: each one is a **correctness** claim (not a percentage), each is cheap to build (hours, not days), each needs no live external service or production-scale data, and each directly demonstrates one of the specific skills on the user's own profile — distributed coordination, concurrency control, failure handling. They're also the four claims most likely to survive an interviewer's immediate follow-up question ("how did you test that?") without hand-waving, because the answer is "here's the test, here's what it does under real concurrency."

M4 (entry-point consolidation) is already resolved by this audit itself — see the finding below — and is listed as P0 only in the sense that it needs to be corrected in any resume/interview framing immediately, not implemented.

P1 holds the next tier: real but either more expensive to set up correctly (M11, M12 — need a running server or mock infrastructure), less flashy but still solid (M5, M6, M8, M9, M10, M13), or dependent on decisions outside this document's scope (how much synthetic load is "enough" to be credible). P2 is genuinely optional — useful supporting color, not something to lead with.

The three rejected candidates (X1–X3) are rejected for different reasons worth keeping distinct: X1 and X2 are rejected because there's nothing real to measure (the mission's instruction not to "manufacture impressive numbers" applies directly — these are gaps, not metrics); X3 is rejected for Part One specifically on cost/noise/scope grounds, not because it's uninteresting.

## 4. Finding that changes a resume-risk calculation

**The "5 entry points funnel into one classified retry engine" framing in `ARCHITECTURE.md` §11.1 is overstated**, and this matters because it's exactly the kind of claim a resume line would compress into "built a unified AI failover system across 5 product surfaces."

Verified via direct source reading (`services/ai_provider_service.py`, `services/websocket_threads.py`, `routes/student/posts/ai.py`, `routes/student/threads/ai.py`, `routes/student/learnora/__init__.py`):

- **2 of 5** entry points (post Q&A, thread meeting-notes/AI-action route trigger) go through `call_ai_response()`, which does use the full 4-category `classify_provider_error()` taxonomy.
- **1 of 5** (standalone Learnora chat) uses a structurally separate `StudyAssistant.stream_response()` loop — it does call the same `classify_provider_error()` function, so classification logic is shared, but the retry/queue-walking mechanics are a different code path, not the same engine.
- **2 of 5** (group-chat `@mention`, per-message AI actions) go through `services/websocket_threads.py`'s `_call_provider_sync`, which **bypasses classification entirely** — it calls `mark_provider_failed()` unconditionally on any failure, meaning these two entry points don't distinguish `KEY_FAULT` from `PROVIDER_TRANSIENT` at all. This is confirmed by the module's own code comment describing this as something "worth its own follow-up," i.e., the codebase already knows this.

This is not a fabrication — classification logic genuinely is shared where it's used, and the design intent clearly is consolidation — but the resume-safe version of this claim is narrower than "5 entry points, 1 engine." See `RESUME_METRICS_AUDIT.md` for the specific recommended rewording.

## 5. Documentation discrepancies found during this audit

Worth naming because they show up in `ARCHITECTURE.md`/`SECURITY.md` themselves and are relevant to how much weight to put on the docs as evidence (none — they're good orientation material, not verification):

1. **CSRF validation.** `ARCHITECTURE.md` §18 states "the server-side validation half of that pattern isn't wired up anywhere in the reviewed routes." `SECURITY.md` §7 contains a later "audit correction" stating it **is** wired up, with specifics. Direct source read of `routes/student/__init__.py::enforce_csrf()` (a `before_request` hook on the whole `student_bp` blueprint, comparing `csrf_token` cookie against `X-CSRF-Token` header, 403 on mismatch) confirms **`SECURITY.md` is correct and `ARCHITECTURE.md` is stale** — CSRF double-submit validation is genuinely implemented and enforced. If using this codebase's security posture as interview material, cite the verified mechanism directly, not either document's prose.
2. **Endpoint/model counts.** See §1 above — 319 endpoints and 52 models verified by grep at this commit, vs. "~250" and "55" in `ARCHITECTURE.md`. Treat the grep counts as current truth; the doc figures are plausible drift from an earlier commit, not evidence of anything deeper.
